# agents.md

Документ для разработчика и ИИ-агентов, работающих над проектом. Кратко: направление, план, стек, договорённости и стиль кода.

## Что это за проект

Улучшенная версия школьного электронного дневника. Берём домашние задания из дневника (платформа Киасуо, API `diaryapi.kiasuo.ru`), анализируем их ИИ, находим нужные страницы учебников и даём ученику решить задание с помощью ИИ. Интерфейс — Telegram-бот.

Проект полуучебный-полуреальный, на стадии разработки.

## Направление и план (этапы)

- [x] **Этап 1. БД** — модели `homeworks`, `homework_files`, `homework_links`, `subjects`, `schedule`; загрузка ДЗ из API Киасуо.
- [x] **Этап 2. Структура учебников** — `structure.json` (параграф → стартовая страница), рендер страниц PDF в PNG.
- [x] **Этап 2.1. Индекс заданий** — скан всех страниц через GigaChat, `<N>.exercises.json`; поиск страниц по номеру без ИИ.
- [x] **Этап 3. Подготовка ДЗ с ИИ** — разбор ДЗ на задачи, определение страниц учебника с нужными заданиями.
- [x] **Этап 4. Решение** — сборка payload (текст + страницы + вложения) → ИИ → ответ в боте; обработчик кнопки «Решить с ИИ».
- [x] **Этап 5. Автоматизация** — отдельный воркер (`worker/main.py`, APScheduler) синкает недели каждые 20 минут и готовит новые ДЗ.

## Логирование

Прикладной код пишет через стандартный `logging`; `print` остался только в демо-блоках `if __name__ == "__main__"`, где печатается сам результат (`ai.solve`, `ai.client`, `db.crud.main`).

- Настройка — `src/logging_setup.py`, функция `setup_logging(name)`. Зовётся один раз на старте процесса: `setup_logging("bot")` в `tg/main.py`, `setup_logging("worker")` в `worker/main.py`, `setup_logging()` (файл `dnevnik.log`) в CLI `net.main`, `ai.prepare`, `ai.scan`. Повторный вызов ничего не дублирует (проверка по уже навешенным хендлерам).
- Куда пишем: консоль (stderr, UTF-8) и файл `logs/<имя процесса>.log` — ротация 5 МБ × 5 архивов, кодировка UTF-8 (иначе на Windows кириллица в файле ломается).
- **У бота и воркера файлы разные не для красоты:** при ротации один процесс переименовывает файл, а второй продолжает в него писать — на Windows это ошибка доступа, и часть строк теряется. Поэтому `bot.log` и `worker.log`, а не один общий.
- Уровень — `LOG_LEVEL` в `.env` (по умолчанию `INFO`; `DEBUG` добавляет подробности). Неверное значение не ломает запуск — берётся `INFO`. Путь к файлу переопределяется `LOG_FILE` (например, если на сервере логи собирает journald), но тогда ротацию настраивает внешняя утилита.
- Формат: `2026-11-04 14:31:40 INFO     net.main: синк недель: 2026-W44` — время, уровень, имя модуля. По имени модуля видно, откуда строка, поэтому в каждом файле `logger = logging.getLogger(__name__)`.
- Файлы в UTF-8. Windows PowerShell 5.1 по умолчанию читает их как ANSI и показывает кракозябры — нужен `-Encoding utf8`; в PowerShell 7 (`pwsh`) достаточно `Get-Content logs\bot.log`.
- Сообщения собираются `%s`-подстановками (`logger.info("ДЗ %d: задач %d", id, n)`), а не f-строками: строка форматируется, только когда её реально пишут.
- `logger.exception(...)` пишет ещё и трейсбек — так логируются падения подготовки ДЗ (одно сломанное ДЗ не останавливает остальные) и ошибка кнопки «Решить с ИИ».
- Что видно в логе: начало и итог синка недель (новых ДЗ, сколько заняло), каждое сохранённое вложение и его размер, «подготовлено задач N» по каждому ДЗ, пропуск по guard'у, пустой разбор (`WARNING`), повторы ИИ с типом ошибки и номером попытки, прогресс скана учебника, старт/стоп воркера и бота.
- Чего в логе нет: токенов, текстов ДЗ и промптов. В предупреждении о повторе ИИ вместо текста задания — предмет и номер попытки.
- Логи aiogram (каждое обновление) и apscheduler идут в тот же root: при `INFO` видно, что бот жив и какие кнопки жмут. Пустой лог = процесс не работает.
- `logs/` в `.gitignore`, папка создаётся сама при старте.

## Развёртывание на новой машине

1. `pip install -r requirements.txt`
2. Скопировать `.env.example` → `.env`, заполнить (DIARY_ID — число из URL дневника).
3. Создать пустую БД и выполнить `alembic upgrade head`: baseline-миграция
   создаёт схему, следующая вставляет 16 предметов (с русскими названиями)
   и недельное расписание. Отдельный сид-скрипт не нужен.
4. Перенести учебники: PDF в git не лежат (244 МБ бинарников), копируются один раз —
   `scp -r files\books user@server:/opt/dnevnik/files/` (или WinSCP/rsync).
   `structure.json` и `exercises.json` приезжают вместе с репозиторием.
5. `python -m worker.main` и `python src\tg\main.py`.

## Ключевые модели и данные

- `subjects.textbook_path` — путь к учебнику (напр. `/algebra/1`).
- `subjects.name_ru` — русское название для бота и промптов (совпадает с предметом в дневнике); `name` — короткий слаг. Оба заполняются сид-миграцией, словарь в коде не нужен. Синк сопоставляет предметы дневника с `name_ru` и пропускает ДЗ с неизвестным предметом, не роняя всю неделю.
- `homeworks` — ДЗ; `homeworks.kiasuo_id` уникален.
  - `lesson_date` — дата урока, к которому ДЗ задали (как в дневнике); `check_at` — «сдать к».
  - В дневнике ДЗ висит на уроке, но показываем его в оба дня: на уроке и в день сдачи (`_homework_days` в `db/crud/main.py`). В карточке урока у задания с другим сроком печатается «Сдать к DD месяц».
  - При синхронизации недели у уже загруженных ДЗ перезаписываются `lesson_date`, `check_at` и текст: в дневнике правят задним числом.
- `homework_tasks` — итог подготовки: `instruction`, `status`, `textbook_paragraphs`, `textbook_pages`, `targets`.
  - `status` только два значения: `ready` или `not_solvable` (всё промежуточное схлопывается).
  - `targets` — список того, что искать на страницах: либо номера заданий (`42.15`), либо «блок + номер» (`Вопросы №3`).
- Enum хранит **значения** (`'ready'`), а не имена — через `values_callable`.

## Как работает подготовка (этап 3)

`ai/prepare.py`, `prepare_homework(homework_id)`:
1. Если у ДЗ уже есть задачи — разбор пропускается и возвращаются готовые: переподготовка тратила ИИ и убивала сохранённые решения (удаляла строки и меняла id, на которые ссылаются кнопки в старых сообщениях). Перечитать принудительно — `prepare_homework(id, force=True)` или `python -m ai.prepare <id> --force`.
2. ИИ-вызов №1 (промпт `ANALYSE_HOMEWORK_PROMT`) — разбивает ДЗ на задачи, возвращает `instruction`, `status`, `needs_textbook`, `textbook_paragraphs`, `textbook_pages`, `targets`.
3. `_resolve_task` доводит статус до финального: `ready`/`not_solvable`. Индекс проверяется первым и для `ready`, и для `needs_materials`: если он нашёл все `targets`, его страницы заменяют страницы из текста ДЗ (там часто словарь или приложение, а не задания).
4. Для заданий из учебника — `search_task_pages`: сначала смотрит готовый индекс заданий (`<N>.exercises.json`, см. `ai/scan.py`) — это мгновенно и бесплатно. Если индекса нет или он нашёл не всё — идём по страницам параграфа **с конца**, на каждой — ИИ-вызов №2 (`FIND_TARGETS_ON_PAGE_PROMT`) «какие из targets есть на странице?», останавливаемся, когда нашли все. Ищет бесплатный GigaChat; не нашёл все → те же страницы перепроверяет GLM; не помогло и это → берём весь параграф.
   К найденным страницам добавляем следующую (`_add_continuation_pages`): номер задания печатают только там, где оно начинается, поэтому продолжение по номеру не находится.
5. Записываем через `rewrite_homework_tasks` (без `force` существующие задачи не трогает). Если разбор не дал ни одной задачи (ИИ не ответил за три попытки или вернул мусор), БД не трогаем и возвращаем то, что там уже есть: иначе прогон с `--force` стёр бы старые задачи, а новых не сохранил.
6. Сессия БД не держится во время работы ИИ: ДЗ, предмет и вложения вычитываются сразу, дальше работают только простые значения (`textbook_path`, `subject_name`), а сессия открывается заново только на сохранение.

Учебники: `get_pages_for_paragraphs` возвращает страницы параграфа **от старта до старта следующего включительно** (граничная страница — там доживают задания). Алгебра/геометрия/информатика — сканы без текста, работает только по картинкам.

## Индекс заданий учебника (скан)

`ai/scan.py` проходит учебник и просит GigaChat выписать номера заданий со страницы. Результат — `<N>.exercises.json` рядом с PDF:

```json
{"textbook_path": "/algebra/1", "total_pages": 478, "models": {...},
 "pages": {"336": {"unit": null, "items": [{"block": null, "number": "43.1"}]}}}
```

- Ключ `pages` — PDF-страница (та же нумерация, что в `textbook_pages`).
- `block` заполняется, когда задания идут под заголовком («Вопросы», «Задания»); `null` — сквозной номер.
- `unit` — заголовок Unit'а со страницы («Unit Two. Town and Its Architecture»), если он там напечатан. Нужен для словарных страниц в конце английского учебника: по ним понятно, к какому Unit'у относятся задания.
- Номера пунктов словаря (слово + транскрипция) — не задания, скан их не выписывает.
- Скан можно прерывать: готовые страницы пропускаются, `--force` пересканирует.
- Текстовая страница (`history`, `physics`) читается текстовым слоем, скан — картинкой. Модели задаются `SCAN_TEXT_MODEL` / `SCAN_IMAGE_MODEL` (по умолчанию `GigaChat-2-Max`: умеет и текст, и картинки). Если на текстовую страницу GigaChat отвечает шаблонным отказом («не обладает собственным мнением»), она автоматически перечитывается картинкой.
- Поиск по индексу — `file_handling.find_pages_by_targets`. Если номер повторяется в разных Unit'ах (английский), без `unit` он считается неоднозначным: Unit берём из текста задания («Unit Two», «Unit 2») или из Unit'а страниц, которые дал разбор ДЗ (`get_page_unit_from_index`).
- Индекс — только карта «номер → страница». В промпт анализа и решения он не уходит: модель видит текст задания и картинки страниц.

## Как работает решение (этап 4)

`ai/solve.py`, `solve_task(task_id)`:
1. `load_solve_context` собирает: `instruction`, `targets`, русское имя предмета, названия вложений, страницы учебника (PNG) и содержимое вложений.
2. Вложения читает `file_handling`: PDF (текстовый слой, скан → первые 6 страниц картинками), DOCX, XLSX, TXT/MD/CSV, картинки. Файл берётся по папке `files/homework/<id>/`, а не по `title` — имя на диске может отличаться. Текст обрезается до 20 000 символов.
3. Тексты вложений уходят в поле `attachments` JSON, картинки — изображениями.
4. Готовый ответ сохраняется в `homework_tasks.solution`; повторный клик отдаёт его из БД. Сохраняется только решение полного набора `targets`.
5. В боте длинный ответ режется на сообщения по 4000 символов (`split_message`), клавиатура вешается на последнее.

Экраны бота: день → урок (текст ДЗ + вложения + задачи) → карточка задачи. Отдельного экрана «Решить с ИИ» со списком задач нет — задачи сразу в уроке. «Назад» ведёт на предыдущий логический экран: с ответа и просмотра страниц — на карточку задачи, с карточки — на урок.

Страницы учебника в боте листаются по всей книге (`pg:<...>:<pdf-страница>`), а не только по страницам задания: старт — первая страница задания, стрелки ±1 до `1..total` (всего страниц — `file_handling.get_page_count`). Страницы задания помечаются в подписи, а в карточке они вынесены отдельными кнопками.

В подписи и на кнопках — **напечатанный** номер страницы (`file_handling.pdf_to_printed`), а не PDF-страница: ученик видит на скане «238», а в PDF это 232. Внутри всё хранится в PDF-страницах.

Страницы задания — это объединение страниц из текста ДЗ и страниц из индекса (а не замена): в английском «Упр.22-27. Стр.238-239» нужны и упражнения (PDF 81–85), и словарь со стр. 238–239 (PDF 232–233).

Ответ ИИ хранится с пометками `**жирный**` — модель выделяет изменённую часть предложения. В бот текст уходит с `parse_mode="HTML"`: `to_html` превращает `**…**` в `<b>…</b>` и экранирует остальное, `split_html_message` режет по строкам и не рвёт теги.

Экраны обновляются в одном сообщении: текст — `edit_text`, страницы — `edit_media`. Telegram не умеет менять тип сообщения, поэтому переход текст → фото и фото → текст делается заменой сообщения (удалить + отправить), а не `edit_*`. Это делает `_show_text` / `_show_photo` в `tg/main.py`; проверка идёт по `message.photo`, а не по перехвату любой `TelegramBadRequest`.

## Автоматизация (этап 5)

`worker/main.py` — отдельный процесс (бот его не запускает): `AsyncIOScheduler` + `CronTrigger(minute="*/20", hour="7-22")`. Вся работа — `net.sync_weeks()`:

- догружает прошлую, текущую и следующую недели (`default_weeks()` возвращает пары «год + номер недели» и считает их от даты, а не «номер + 1» — на стыке лет номера перескакивают);
- существующие ДЗ обновляет (даты, текст), новые — добавляет и готовит; уже готовые повторно не трогает (guard в `prepare_homework`);
- ошибка подготовки одного ДЗ не останавливает остальные.

CLI `python -m net.main` вызывает ту же функцию, поэтому поведение ручного и фонового запуска одинаковое. `python -m worker.main --once` — один прогон и выход (лок-защита действует и здесь).

Настройки расписания: `max_instances=1` (второй прогон не начинается, пока идёт первый), `coalesce=True` и `misfire_grace_time=300` (после сна/тормозов пропущенные тики схлопываются в один), первый тик сразу после старта, если сейчас рабочие часы; ночью (23:00–06:59) дневник не дёргается.

Воркер должен быть **один**: `Token.refresh()` перезаписывает `.env`, два процесса затрут токены друг друга. Это защищено advisory-локой Postgres (`pg_try_advisory_lock`): второй экземпляр сразу выходит с сообщением «воркер уже запущен». Лок снимается сам при падении процесса.

`Token.refresh()` перезаписывает `.env` по ключам (`update_env`), путь — от корня проекта, поэтому запуск из `src` файл не ломает.

## Договорённости и решения

- Храним только **финальные** статусы; промежуточные (`needs_materials`, `needs_clarification`) не сохраняем — «добиваем» внутри прогона.
- В `homework_tasks` не храним `position`, `missing_info` и дубли вложений — вложения берём из `homework` при решении.
- Сужаем страницы **по одной странице с конца** (а не пачкой картинок): на пачке 10+ картинок модель путает номера, на одной — читает точно.
- Не завязаны на формат «N.M»: `targets` универсальны (номера заданий или «блок + номер»).
- Для ИИ передаём **русское** имя предмета из `subjects.name_ru` (строка уже загружена вместе с предметом — лишнего запроса нет).
- Названия предметов для экранов бота кэшируются в памяти при старте (`load_subject_names`), поэтому нажатия кнопок не ходят в БД за переводом.
- Пути к файлам (сертификат, `files/books`, `files/homework`) и `.env` — абсолютные от корня проекта, чтобы запуск из любой папки работал (в т.ч. `cd src; python -m worker.main`).
- Экран бота — последнее сообщение в чате (`_last_message_id`): если ниже экрана уже ушёл файл, экран переносится вниз (удалить + отправить), иначе длинный ответ разрывается на «часть 1 → файл → часть 2».
- История миграций свёрнута: `84627560cb00_initial_schema` создаёт всю схему, `1f3c9b7a2e50_seed_subjects_and_schedule` вставляет предметы и расписание. Новые изменения схемы — только новыми миграциями поверх.
- Провайдер и модель ИИ — через `src/ai/client.py`. Анализ и решение — `AI_PROVIDER` (`routerai`/`gigachat`), `AI_MODEL`, `AI_REASONING_EFFORT` (по умолчанию `medium`), `AI_TEMPERATURE` (по умолчанию `0`). Поиск номеров на страницах — отдельный `AI_SEARCH_PROVIDER` (по умолчанию бесплатный `gigachat`): вызовов много и по одной странице, а при промахе те же страницы перепроверяет основная модель. Провайдера RouterAI не пришпиливаем: дешёвые провайдеры не читают сканы.
- `targets` чистим от ведущего «№»/«#» и слов-префиксов («Упражнение 22» → «22»): модели возвращают «№43.4», а индекс и разбор параграфа ждут «43.4». Нормализация живёт в `file_handling.normalize_target`.
- Температура по умолчанию `0` (`AI_TEMPERATURE`): без неё разбор одного и того же ДЗ получается разным от запуска к запуску — то 1 задача, то 4.
- `textbook_pages` всегда хранит **PDF-страницы**. Модель читает текст ДЗ, поэтому её страницы — напечатанные номера; в `_resolve_task` они переводятся через `printed_to_pdf`, которая учитывает `page_offset` и `skipped_pages` (в английском учебнике пропущено 7 страниц, поэтому одного offset мало). Страницы из поиска и индекса уже PDF.
- В ответе ИИ не должно быть служебных фраз («Это задание — выучить слова», «Объясняю значения», «Ответ: предложения переведены выше») и дублирующей строки «Ответ:» после готового списка; это задано в `SOLVE_REQUIREMENTS`. Жирным выделяется только изменённая часть предложения.

## Стиль кода

- Функции и переменные — `snake_case`, классы — `CamelCase`.
- Асинхронный код: `async def`, `async with SessionLocal() as session`, aiohttp/SQLAlchemy async.
- Модули импортируются как пакеты от `src` (`from db.crud.main import ...`, `from ai.client import ...`).
- Доступ к БД — только через функции в `db/crud/main.py`, логика — по модулям (net/ai/file_handling/tg).
- Промпты — все в `ai/promts.py`, отдельными константами.
- Комментарии и docstring-и — по-русски.
- Неиспользуемое вычищается (удаляем старые модели/функции/файлы, а не оставляем «на память»).
- Секреты — только в `.env`, в коде не хардкодим.

## Известные ограничения / TODO

- **Нет способа перерешать задачу:** ответ лежит в `homework_tasks.solution`, повторный клик отдаёт его из БД. Нужен `force` в `solve_task` и кнопка «🔄 Перерешать» на экране ответа (пункт отложен).
- **Не подготовлены 133 ДЗ** (в т.ч. ~49 с 1 октября): на них нет кнопки «Решить с ИИ». Лечится прогоном `prepare_homework` по пустым — долго и дорого, отложено. Осторожно: guard не даёт перечитывать ДЗ с задачами, для них нужен `--force` (см. ниже про старые страницы).
- **`.doc` (Word 97-2003) не читается.** Это бинарный OLE-контейнер, а не ZIP, как `.docx`, поэтому `_docx_text` (zipfile + XML) его не разбирает; отдельного парсера в проекте нет. Варианты: требовать `.docx`, конвертировать через LibreOffice (`soffice --headless --convert-to docx`) или тянуть `olefile`+парсер — решаем, когда такие вложения реально пойдут.
- **Ссылки (`homework_links`) не скачиваются:** модель видит только заголовок ссылки.
- **Гуманитарные задания** вроде «прочитать §11» модель помечает как `ready` (семантически стоило бы `not_solvable`) — промпт можно доуточнить.
- **Сужение страниц** может «не найти все targets» → fallback на весь параграф; качество зависит от модели.
- **Индекс заданий — подсказка, а не истина:** бесплатный GigaChat иногда пропускает номера, особенно на страницах с вложенными подпунктами. Тогда `find_pages_by_targets` не находит всё и разбор идёт по страницам параграфа через ИИ (дороже и менее точно), а в крайнем случае берётся весь параграф. Перескан нужной страницы (`python -m ai.scan <book> --from N --to N --force`) чинит индекс для всех будущих заданий; сканировать всю книгу заново не нужно.
- **Старые `textbook_pages`** посчитаны по прежним правилам (до фикса `printed_to_pdf`) — часть задач открывает не ту страницу. Лечится переподготовкой конкретного ДЗ: `python -m ai.prepare <id> --force` (решение при этом обнулится).
- **В тексте задания остаются печатные номера страниц** («на страницах 238–239»), даже если задания на других страницах. В карточке рядом печатается фактический список страниц задания, поэтому автоподмена текста не делается: в английском одно и то же задание ссылается и на упражнения, и на словарь, и слепая замена сломает вторую ссылку.
- **Обработка ошибок ИИ:** в боте ошибка перехвачена («Не получилось решить задание. Попробуй ещё раз»), но повторного авто-запроса и разбора причин (`LengthFinishReasonError` и т.п.) нет.
- **Git не инициализирован.** `.gitignore`, `requirements.txt`, `.env.example` готовы; при `git init` проверить, что `.env` не попал в индекс.
- **Токены дневника светились в `test.py`** (файл удалён) — после перелогина в дневнике обновить `ACCESS_TOKEN`/`REFRESH_TOKEN` в `.env`.
