# agents.md

Документ для разработчика и ИИ-агентов, работающих над проектом. Кратко: направление, план, стек, договорённости и стиль кода.

## Что это за проект

Улучшенная версия школьного электронного дневника. Берём домашние задания из дневника (платформа Киасуо, API `diaryapi.kiasuo.ru`), анализируем их ИИ, находим нужные страницы учебников и даём ученику решить задание с помощью ИИ. Интерфейс — Telegram-бот.

Проект полуучебный-полуреальный, на стадии разработки.

## Направление и план (этапы)

- [x] **Этап 1. БД** — модели `homeworks`, `homework_files`, `homework_links`, `subjects`, `schedule`; загрузка ДЗ из API Киасуо.
- [x] **Этап 2. Структура учебников** — `structure.json` (параграф → стартовая страница), рендер страниц PDF в PNG.
- [x] **Этап 2.1. Индекс заданий** — скан всех страниц через GigaChat, `<N>.exercises.json`; поиск страниц по номеру без ИИ.
- [x] **Этап 3. Подготовка ДЗ с ИИ** — разбор ДЗ на задачи, определение страниц учебника с нужными заданиями.
- [x] **Этап 4. Решение** — сборка payload (текст + страницы + вложения) → ИИ → ответ в боте; обработчик кнопки «Решить с ИИ».
- [x] **Этап 5. Автоматизация** — отдельный воркер (`worker/main.py`, APScheduler) синкает недели каждые 20 минут и готовит новые ДЗ.

## Логирование

Прикладной код пишет через стандартный `logging`; `print` остался только в демо-блоках `if __name__ == "__main__"`, где печатается сам результат (`ai.solve`, `ai.client`, `db.crud.main`).

- Настройка — `src/logging_setup.py`, функция `setup_logging(name)`. Зовётся один раз на старте процесса: `setup_logging("bot")` в `tg/main.py`, `setup_logging("worker")` в `worker/main.py`, `setup_logging()` (файл `dnevnik.log`) в CLI `net.main`, `ai.prepare`, `ai.scan`. Повторный вызов ничего не дублирует (проверка по уже навешенным хендлерам).
- Куда пишем: консоль (stderr, UTF-8) и файл `logs/<имя процесса>.log` — ротация 5 МБ × 5 архивов, кодировка UTF-8 (иначе на Windows кириллица в файле ломается).
- **У бота и воркера файлы разные не для красоты:** при ротации один процесс переименовывает файл, а второй продолжает в него писать — на Windows это ошибка доступа, и часть строк теряется. Поэтому `bot.log` и `worker.log`, а не один общий.
- Уровень — `LOG_LEVEL` в `.env` (по умолчанию `INFO`; `DEBUG` добавляет подробности). Неверное значение не ломает запуск — берётся `INFO`. Путь к файлу переопределяется `LOG_FILE` (например, если на сервере логи собирает journald), но тогда ротацию настраивает внешняя утилита.
- Формат: `2026-11-04 14:31:40 INFO     net.main [tg:829092870]: ИИ: решение задачи 12 (Алгебра)…` — время, уровень, имя модуля, telegram id того, кто нажал кнопку (только у бота), сообщение. По имени модуля видно, откуда строка, поэтому в каждом файле `logger = logging.getLogger(__name__)`.
- **Время в логах — пояс процесса:** `asctime` берёт локальное время, а его задаёт `TZ` в systemd-юните (`Asia/Krasnoyarsk`). Префикс `Nov 16 18:52:21 server python[7713]:` в `journalctl` рисует уже systemd по **системному** поясу сервера, поэтому один раз надо поменять и его: `sudo timedatectl set-timezone Asia/Krasnoyarsk`. Если поменять только юнит, в файле будет красноярское время, а в journalctl — московское.
- **Кто нажал кнопку:** `UserLogDispatcher` в `tg/main.py` (наследник `aiogram.Dispatcher`) переопределяет `feed_update`: берёт `from_user.id`, вешает его через `bind_user` из `logging_setup` на весь апдейт и пишет строку `апдейт 829092899: кнопка day:2026:46:3`. `UserFormatter` печатает id как `[tg:<id>]`, поэтому метка есть и в строках обработчика (БД, файлы, OCR, вызовы ИИ), и в итоговой `aiogram.event: Update ... is handled` — она пишется в `finally` того же `feed_update`, то есть внутри области. Outer-middleware для этого не годится: его `finally` срабатывает раньше, чем aiogram пишет итог. У воркера и CLI метки нет — там её некому поставить.
- **Обращения к ИИ логируются отдельно:** `ai/solve.py` пишет две строки на каждый вызов — `ИИ: решение задачи 12 (Алгебра), модель z-ai/glm-5.3-flash, номеров 2` и `ИИ: … готово за 12.3 с, символов 2745, 0.123 ₽` (у пересказа в первой строке ещё время OCR и число страниц). Если ответ уже лежал в БД, пишется `ответ уже есть в БД, ИИ не вызывается` — по этому видно, что денег не потратили.
- Файлы в UTF-8. Windows PowerShell 5.1 по умолчанию читает их как ANSI и показывает кракозябры — нужен `-Encoding utf8`; в PowerShell 7 (`pwsh`) достаточно `Get-Content logs\bot.log`.
- Сообщения собираются `%s`-подстановками (`logger.info("ДЗ %d: задач %d", id, n)`), а не f-строками: строка форматируется, только когда её реально пишут.
- `logger.exception(...)` пишет ещё и трейсбек — так логируются падения подготовки ДЗ (одно сломанное ДЗ не останавливает остальные) и ошибка кнопки «Решить с ИИ».
- Что видно в логе: начало и итог синка недель (новых ДЗ, сколько заняло), каждое сохранённое вложение и его размер, «подготовлено задач N» по каждому ДЗ, пропуск по guard'у, пустой разбор (`WARNING`), повторы ИИ с типом ошибки и номером попытки, прогресс скана учебника, старт/стоп воркера и бота.
- Чего в логе нет: токенов, текстов ДЗ и промптов. В предупреждении о повторе ИИ вместо текста задания — предмет и номер попытки.
- Логи aiogram (каждое обновление) и apscheduler идут в тот же root: при `INFO` видно, что бот жив и какие кнопки жмут. Пустой лог = процесс не работает.
- `logs/` в `.gitignore`, папка создаётся сама при старте.

## Развёртывание на новой машине

1. `pip install -r requirements.txt` (нужен Python **3.11+**: `logging_setup` использует `logging.getLevelNamesMapping()`, появившийся в 3.11).
2. Скопировать `.env.example` → `.env`, заполнить (DIARY_ID — число из URL дневника).
3. Создать пустую БД и выполнить `alembic upgrade head` из корня проекта: `prepend_sys_path = %(here)s/src` в `alembic.ini`, поэтому `PYTHONPATH=src` не нужен. Baseline-миграция создаёт схему, следующая вставляет 16 предметов (с русскими названиями) и недельное расписание. Отдельный сид-скрипт не нужен.
4. Перенести учебники: PDF в git не лежат (244 МБ бинарников), копируются один раз —
   `scp -r files\books user@server:/opt/dnevnik/files/` (или WinSCP/rsync).
   `structure.json` и `exercises.json` приезжают вместе с репозиторием.
5. `python -m worker.main` и `python src\tg\main.py`.

## Запуск на сервере (Linux, systemd)

Проверено на Ubuntu/Debian; на Windows-сервере — те же шаги, но вместо systemd нужен планировщик/служба. Бери **Ubuntu 24.04** (в ней Python 3.12): в 22.04 по умолчанию 3.10, а проекту нужен 3.11+ — там придётся ставить 3.11 из deadsnakes PPA.

```bash
# 1. Код и окружение
git clone https://github.com/G0R0X/dnevnik.git /opt/dnevnik
cd /opt/dnevnik
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. Секреты: .env только на сервере, в git его нет
scp .env user@server:/opt/dnevnik/.env
chown dnevnik:dnevnik /opt/dnevnik/.env
chmod 600 /opt/dnevnik/.env
```

`.env` **обязан быть записываемым** для сервисного пользователя: `Token.refresh()` перезаписывает в нём `ACCESS_TOKEN`/`REFRESH_TOKEN` через `update_env`. Права `600` и владелец `dnevnik` (не root) — иначе воркер упадёт на первом обновлении токена.

`Token.refresh()` обновляет и `os.environ`, и `.env`: воркер создаёт новый `Token()` на каждый синк (раз в 20 минут), и без обновления окружения следующий прогон прочитал бы стартовые токены. Если `.env` нет (контейнер, где секреты приходят переменными окружения), `update_env` создаёт его; если файл только для чтения — пишется `WARNING`, процесс продолжает работать на обновлённых токенах до перезапуска. Поэтому на PaaS секреты надо либо монтировать файлом на volume, либо после каждого рестарта обновлять `ACCESS_TOKEN`/`REFRESH_TOKEN` в настройках сервиса.

```bash
# 3. PostgreSQL: отдельный пользователь и база
sudo apt update && sudo apt install -y postgresql
sudo -u postgres createuser dnevnik --pwprompt
sudo -u postgres createdb dnevnik -O dnevnik
# DATABASE_URL=postgresql+asyncpg://dnevnik:пароль@localhost:5432/dnevnik

# 4. Схема (из корня проекта, PYTHONPATH не нужен)
cd /opt/dnevnik && .venv/bin/alembic upgrade head

# 5. Учебники (единственное, чего нет в git)
rsync -av files/books/ user@server:/opt/dnevnik/files/books/

# 6. Сервисы
sudo cp deploy/dnevnik-bot.service deploy/dnevnik-worker.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now dnevnik-worker dnevnik-bot
```

Юниты лежат в `deploy/`: `WorkingDirectory=/opt/dnevnik/src` (нужно для `python -m`), `TZ=Asia/Krasnoyarsk`, `Restart=always`. Воркер должен быть **один** — второй экземпляр выходит по advisory-локе, но два юнита на одном хосте всё равно не нужны.

Часовой пояс — не косметика: сервер обычно в UTC, а `worker` считает «сегодня» и `default_weeks()` от локальной даты, cron настроен на 7–22. Без `TZ=Asia/Krasnoyarsk` синк ходил бы в 7–22 по Москве (11:00–02:40 по Красноярску), а ночью «сегодня» было бы вчерашним. Системный пояс сервера меняется отдельно — `sudo timedatectl set-timezone Asia/Krasnoyarsk`, иначе `journalctl` продолжит печатать префиксы по старому поясу.

Порты открывать не нужно: бот работает на long polling, наружу нужны только исходящие HTTPS к `api.telegram.org`, `diaryapi.kiasuo.ru`, RouterAI и GigaChat.

Проверка после запуска:

```bash
systemctl status dnevnik-bot dnevnik-worker
journalctl -u dnevnik-worker -n 50 --no-pager
tail -f /opt/dnevnik/logs/worker.log
cd /opt/dnevnik/src && ../.venv/bin/python -m net.main --week 44 --no-prepare   # одна неделя, без ИИ
```

Обновление на сервере — одной командой: `deploy/deploy.sh`. Скрипт отказывается работать при незакоммиченных правках (иначе `git pull` их снесёт или упадёт), тянет `--ff-only`, при новых файлах в `alembic/versions/` сначала делает дамп БД (`~/backups/`), потом `alembic upgrade head`, при изменении `requirements*.txt` — `pip install`, и перезапускает службы только если менялся `src/` или зависимости. `.env`, `files/homework/`, `files/books/*.pdf` и `logs/` скрипт не трогает: они в `.gitignore`.

Адрес зеркала Bot API перепроверяется сам: `deploy/bot-api-ip.sh` + `dnevnik-bot-api-ip.timer`. Ставится один раз:

```bash
# из корня репозитория
sudo cp deploy/dnevnik-bot-api-ip.service deploy/dnevnik-bot-api-ip.timer /etc/systemd/system/
# путь в юните под свой репозиторий (в репозитории он /opt/dnevnik, на домашнем сервере — /home/gorox/projects/dnevnik)
sudo sed -i "s#/opt/dnevnik#$PWD#g" /etc/systemd/system/dnevnik-bot-api-ip.service
sudo systemctl daemon-reload
sudo systemctl enable --now dnevnik-bot-api-ip.timer
```

Проверка: `systemctl list-timers dnevnik-bot-api-ip.timer`, лог — `journalctl -u dnevnik-bot-api-ip -n 40 --no-pager`. Таймер правит `/etc/hosts`, поэтому без `sudo` скрипт не запускается (и перезапускает бота только при смене адреса).

Бэкап: `pg_dump` по cron. ДЗ восстановятся синком, а сохранённые `homework_tasks.solution` — нет.

```bash
pg_dump -U dnevnik dnevnik | gzip > /var/backups/dnevnik-$(date +%F).sql.gz
```

Секреты в git не попадают (`.env` в `.gitignore`, в истории его нет). Если понадобится CI — ключи кладутся в GitHub Actions Secrets, а не в workflow-файлы, тем более в публичном репозитории.

## Ключевые модели и данные

- `subjects.textbook_path` — путь к учебнику (напр. `/algebra/1`).
- `subjects.name_ru` — русское название для бота и промптов (совпадает с предметом в дневнике); `name` — короткий слаг. Оба заполняются сид-миграцией, словарь в коде не нужен. Синк сопоставляет предметы дневника с `name_ru` и пропускает ДЗ с неизвестным предметом, не роняя всю неделю.
- `homeworks` — ДЗ; `homeworks.kiasuo_id` уникален.
  - `lesson_date` — дата урока, к которому ДЗ задали (как в дневнике); `check_at` — «сдать к».
  - ДЗ показывается **только в день сдачи** (`_homework_days` в `db/crud/main.py` фильтрует по `check_at`): ученику нужно видеть задание тогда, когда его надо сдать, а не в день, когда его выдали. `lesson_date` по-прежнему хранится (дата урока из дневника, по ней идёт синк), но в экранах не используется. Подписи «Сдать к …» в карточке урока нет — она стала бы лишней.
  - При синхронизации недели у уже загруженных ДЗ перезаписываются `lesson_date`, `check_at` и текст: в дневнике правят задним числом.
- `homework_tasks` — итог подготовки: `instruction`, `status`, `textbook_paragraphs`, `textbook_pages`, `targets`.
  - `status` — `ready`, `retell` или `not_solvable` (всё промежуточное схлопывается). `retell` — задание сводится к чтению/пересказу параграфа: страницы параграфа сохраняются, чтобы бот мог их показать, а ИИ — пересказать текст.
  - `targets` — список того, что искать на страницах: либо номера заданий (`42.15`), либо «блок + номер» (`Вопросы №3`).
- Enum хранит **значения** (`'ready'`), а не имена — через `values_callable`.

## Как работает подготовка (этап 3)

`ai/prepare.py`, `prepare_homework(homework_id)`:
1. Если у ДЗ уже есть задачи — разбор пропускается и возвращаются готовые: переподготовка тратила ИИ и убивала сохранённые решения (удаляла строки и меняла id, на которые ссылаются кнопки в старых сообщениях). Перечитать принудительно — `prepare_homework(id, force=True)` или `python -m ai.prepare <id> --force`.
2. ИИ-вызов №1 (промпт `ANALYSE_HOMEWORK_PROMT`) — разбивает ДЗ на задачи, возвращает `instruction`, `status`, `needs_textbook`, `textbook_paragraphs`, `textbook_pages`, `targets`.
3. `_resolve_task` доводит статус до финального: `ready`/`retell`/`not_solvable`. Индекс проверяется первым и для `ready`, и для `needs_materials`: если он нашёл все `targets`, его страницы заменяют страницы из текста ДЗ (там часто словарь или приложение, а не задания). Для `retell` страницы берутся из `structure.json` через `get_pages_for_paragraphs(..., include_boundary=False)` — без индекса и ИИ; первая страница следующего параграфа отрезается, потому что относится уже к другой теме. Страницы из текста ДЗ для пересказа — только запасной вариант, когда параграфов нет: рядом часто стоят соседние задания («§5–6, стр. 84 №1»), которые к пересказу не относятся. Если параграфа нет в `structure.json` или у предмета нет учебника, задача честно уходит в `not_solvable`. После разбора `_split_retell_task` делит пересказ нескольких параграфов на отдельную задачу на каждый параграф («§27.28» → §27 и §28), инструкция переписывается под один номер, страницы считаются заново. Параграфы, которые в `structure.json` начинаются на одной странице (в истории §5–6 — один раздел), остаются одной задачей; если хоть один параграф не нашёлся, задачу не делят.
4. Для заданий из учебника — `search_task_pages`: сначала смотрит готовый индекс заданий (`<N>.exercises.json`, см. `ai/scan.py`) — это мгновенно и бесплатно. Если индекса нет или он нашёл не всё — идём по страницам параграфа **с конца**, на каждой — ИИ-вызов №2 (`FIND_TARGETS_ON_PAGE_PROMT`) «какие из targets есть на странице?», останавливаемся, когда нашли все. Ищет бесплатный GigaChat; не нашёл все → те же страницы перепроверяет GLM; не помогло и это → берём весь параграф.
   К найденным страницам добавляем следующую (`_add_continuation_pages`): номер задания печатают только там, где оно начинается, поэтому продолжение по номеру не находится.
5. Записываем через `rewrite_homework_tasks` (без `force` существующие задачи не трогает). Если разбор не дал ни одной задачи (ИИ не ответил за три попытки или вернул мусор), БД не трогаем и возвращаем то, что там уже есть: иначе прогон с `--force` стёр бы старые задачи, а новых не сохранил.
6. Сессия БД не держится во время работы ИИ: ДЗ, предмет и вложения вычитываются сразу, дальше работают только простые значения (`textbook_path`, `subject_name`), а сессия открывается заново только на сохранение.

Учебники: `get_pages_for_paragraphs` возвращает страницы параграфа **от старта до старта следующего включительно** (граничная страница — там доживают задания). Алгебра/геометрия/информатика — сканы без текста, работает только по картинкам.

## Индекс заданий учебника (скан)

`ai/scan.py` проходит учебник и просит GigaChat выписать номера заданий со страницы. Результат — `<N>.exercises.json` рядом с PDF:

```json
{"textbook_path": "/algebra/1", "total_pages": 478, "models": {...},
 "pages": {"336": {"unit": null, "items": [{"block": null, "number": "43.1"}]}}}
```

- Ключ `pages` — PDF-страница (та же нумерация, что в `textbook_pages`).
- `block` заполняется, когда задания идут под заголовком («Вопросы», «Задания»); `null` — сквозной номер.
- `unit` — заголовок Unit'а со страницы («Unit Two. Town and Its Architecture»), если он там напечатан. Нужен для словарных страниц в конце английского учебника: по ним понятно, к какому Unit'у относятся задания.
- Номера пунктов словаря (слово + транскрипция) — не задания, скан их не выписывает.
- Скан можно прерывать: готовые страницы пропускаются, `--force` пересканирует.
- Текстовая страница (`history`, `physics`) читается текстовым слоем, скан — картинкой. Модели задаются `SCAN_TEXT_MODEL` / `SCAN_IMAGE_MODEL` (по умолчанию `GigaChat-2-Max`: умеет и текст, и картинки). Если на текстовую страницу GigaChat отвечает шаблонным отказом («не обладает собственным мнением»), она автоматически перечитывается картинкой.
- Поиск по индексу — `file_handling.find_pages_by_targets`. Если номер повторяется в разных Unit'ах (английский), без `unit` он считается неоднозначным: Unit берём из текста задания («Unit Two», «Unit 2») или из Unit'а страниц, которые дал разбор ДЗ (`get_page_unit_from_index`).
- Индекс — только карта «номер → страница». В промпт анализа и решения он не уходит: модель видит текст задания и картинки страниц.

## Как работает решение (этап 4)

`ai/solve.py`, `solve_task(task_id)`:
1. `load_solve_context` собирает: `instruction`, `targets`, русское имя предмета, названия вложений, страницы учебника (PNG) и содержимое вложений. Для `retell` вложения и PNG-страницы не читаются: нужен только текст параграфа.
2. Вложения читает `file_handling`: PDF (текстовый слой, скан → первые 6 страниц картинками), DOCX, XLSX, TXT/MD/CSV, картинки. Файл берётся по папке `files/homework/<id>/`, а не по `title` — имя на диске может отличаться. Текст обрезается до 20 000 символов.
3. Тексты вложений уходят в поле `attachments` JSON, картинки — изображениями.
4. Готовый ответ сохраняется в `homework_tasks.solution`; повторный клик отдаёт его из БД. Сохраняется только решение полного набора `targets`.
5. В боте длинный ответ режется на сообщения по 4000 символов (`split_message`), клавиатура вешается на последнее.

**Пересказ (`retell`)** идёт отдельной веткой, без картинок в платную модель:

1. `ai/page_text.get_pages_text` читает страницы параграфа по порядку. Сначала пробует текстовый слой PDF (история — мгновенно и бесплатно). Сканы (алгебра, геометрия, информатика, английский) и физику распознаёт OCR-модель: в физике слой формально есть, но слова разорваны пробелами, а формулы рассыпаются на символы, поэтому `FORCE_OCR_SUBJECTS` распознаёт её всегда. Провайдер и параллельность задаются `OCR_PROVIDER` / `OCR_MODEL` / `OCR_CONCURRENCY` (по умолчанию `routerai` + `AI_MODEL` — быстрее всех проверенных, ~3 с на страницу, 4 страницы разом); `OCR_PROVIDER=gigachat` — бесплатно, но free-тариф пропускает только один запрос одновременно, поэтому там `OCR_CONCURRENCY` больше 1 только добавляет 429. Распознавание идёт с `reasoning_effort="none"`: параметр отправляется явно, потому что без него RouterAI включает reasoning по умолчанию и страница дорожает почти вдвое (reasoning-токенов было 4200–6300 на страницу при ответе ~800 токенов). OCR-промпт `TRANSCRIBE_PAGE_PROMT` просит простую запись формул (`x^2`, `sqrt(x)`, `(a+b)/c`) без LaTeX.
2. Текст уходит в платную модель с промптом `RETELL_PARAGRAPH_PROMT`: связный пересказ, только по тексту, без выдуманных формул; несколько параграфов — по порядку. План модель держит в уме, в ответ он не попадает (`_strip_plan` вырезает его, если модель всё же начала с плана). Ответ сохраняется в `solution`, поэтому повторный клик не OCR-ит и не генерирует заново.
3. Текст страниц нигде не кэшируется: при перерешивании его придётся получать заново, но такого сценария пока нет.

Экраны бота: день → урок (текст ДЗ + вложения + задачи) → карточка задачи. Отдельного экрана «Решить с ИИ» со списком задач нет — задачи сразу в уроке. «Назад» ведёт на предыдущий логический экран: с ответа и просмотра страниц — на карточку задачи, с карточки — на урок.

Страницы учебника в боте листаются по всей книге (`pg:<...>:<pdf-страница>`), а не только по страницам задания: старт — первая страница задания, стрелки ±1 до `1..total` (всего страниц — `file_handling.get_page_count`). Страницы задания помечаются в подписи, а в карточке они вынесены отдельными кнопками.

В подписи и на кнопках — **напечатанный** номер страницы (`file_handling.pdf_to_printed`), а не PDF-страница: ученик видит на скане «238», а в PDF это 232. Внутри всё хранится в PDF-страницах.

Страницы задания — это объединение страниц из текста ДЗ и страниц из индекса (а не замена): в английском «Упр.22-27. Стр.238-239» нужны и упражнения (PDF 81–85), и словарь со стр. 238–239 (PDF 232–233).

Ответ ИИ хранится с пометками `**жирный**` — модель выделяет изменённую часть предложения. В бот текст уходит с `parse_mode="HTML"`: `to_html` превращает `**…**` в `<b>…</b>` и экранирует остальное, `split_html_message` режет по строкам и не рвёт теги.

Экраны обновляются в одном сообщении: текст — `edit_text`, страницы — `edit_media`. Telegram не умеет менять тип сообщения, поэтому переход текст → фото и фото → текст делается заменой сообщения (удалить + отправить), а не `edit_*`. Это делает `_show_text` / `_show_photo` в `tg/main.py`; проверка идёт по `message.photo`, а не по перехвату любой `TelegramBadRequest`.

## Автоматизация (этап 5)

`worker/main.py` — отдельный процесс (бот его не запускает): `AsyncIOScheduler` + `CronTrigger(minute="*/20", hour="7-22")`. Вся работа — `net.sync_weeks()`:

- догружает прошлую, текущую и следующую недели (`default_weeks()` возвращает пары «год + номер недели» и считает их от даты, а не «номер + 1» — на стыке лет номера перескакивают);
- существующие ДЗ обновляет (даты, текст), новые — добавляет и готовит; уже готовые повторно не трогает (guard в `prepare_homework`);
- ошибка подготовки одного ДЗ не останавливает остальные.

CLI `python -m net.main` вызывает ту же функцию, поэтому поведение ручного и фонового запуска одинаковое. `python -m worker.main --once` — один прогон и выход (лок-защита действует и здесь).

Настройки расписания: `max_instances=1` (второй прогон не начинается, пока идёт первый), `coalesce=True` и `misfire_grace_time=300` (после сна/тормозов пропущенные тики схлопываются в один), первый тик сразу после старта, если сейчас рабочие часы; ночью (23:00–06:59) дневник не дёргается.

Воркер должен быть **один**: `Token.refresh()` перезаписывает `.env`, два процесса затрут токены друг друга. Это защищено advisory-локой Postgres (`pg_try_advisory_lock`): второй экземпляр сразу выходит с сообщением «воркер уже запущен». Лок снимается сам при падении процесса.

`Token.refresh()` перезаписывает `.env` по ключам (`update_env`), путь — от корня проекта, поэтому запуск из `src` файл не ломает.

## Договорённости и решения

- Храним только **финальные** статусы; промежуточные (`needs_materials`, `needs_clarification`) не сохраняем — «добиваем» внутри прогона.
- В `homework_tasks` не храним `position`, `missing_info` и дубли вложений — вложения берём из `homework` при решении.
- Сужаем страницы **по одной странице с конца** (а не пачкой картинок): на пачке 10+ картинок модель путает номера, на одной — читает точно.
- Не завязаны на формат «N.M»: `targets` универсальны (номера заданий или «блок + номер»).
- Для ИИ передаём **русское** имя предмета из `subjects.name_ru` (строка уже загружена вместе с предметом — лишнего запроса нет).
- Названия предметов для экранов бота кэшируются в памяти при старте (`load_subject_names`), поэтому нажатия кнопок не ходят в БД за переводом.
- Пути к файлам (сертификат, `files/books`, `files/homework`) и `.env` — абсолютные от корня проекта, чтобы запуск из любой папки работал (в т.ч. `cd src; python -m worker.main`).
- Экран бота — последнее сообщение в чате (`_last_message_id`): если ниже экрана уже ушёл файл, экран переносится вниз (удалить + отправить), иначе длинный ответ разрывается на «часть 1 → файл → часть 2».
- История миграций свёрнута: `84627560cb00_initial_schema` создаёт всю схему, `1f3c9b7a2e50_seed_subjects_and_schedule` вставляет предметы и расписание. Новые изменения схемы — только новыми миграциями поверх.
- Провайдер и модель ИИ — через `src/ai/client.py`. Анализ и решение — `AI_PROVIDER` (`routerai`/`gigachat`), `AI_MODEL`, `AI_REASONING_EFFORT` (по умолчанию `medium`), `AI_TEMPERATURE` (по умолчанию `0`). Поиск номеров на страницах — отдельный `AI_SEARCH_PROVIDER` (по умолчанию бесплатный `gigachat`): вызовов много и по одной странице, а при промахе те же страницы перепроверяет основная модель. Распознавание страниц для пересказа — отдельные `OCR_PROVIDER` (по умолчанию `routerai`: сканы читает хорошо и держит 4 запроса параллельно), `OCR_MODEL` и `OCR_CONCURRENCY`; у `gigachat` в OCR смысла в параллельности нет — free-тариф пропускает один запрос одновременно. Провайдера RouterAI не пришпиливаем: дешёвые провайдеры не читают сканы.
- `targets` чистим от ведущего «№»/«#» и слов-префиксов («Упражнение 22» → «22»): модели возвращают «№43.4», а индекс и разбор параграфа ждут «43.4». Нормализация живёт в `file_handling.normalize_target`.
- Температура по умолчанию `0` (`AI_TEMPERATURE`): без неё разбор одного и того же ДЗ получается разным от запуска к запуску — то 1 задача, то 4.
- `textbook_pages` всегда хранит **PDF-страницы**. Модель читает текст ДЗ, поэтому её страницы — напечатанные номера; в `_resolve_task` они переводятся через `printed_to_pdf`, которая учитывает `page_offset` и `skipped_pages` (в английском учебнике пропущено 7 страниц, поэтому одного offset мало). Страницы из поиска и индекса уже PDF.
- В ответе ИИ не должно быть служебных фраз («Это задание — выучить слова», «Объясняю значения», «Ответ: предложения переведены выше») и дублирующей строки «Ответ:» после готового списка; это задано в `SOLVE_REQUIREMENTS`. Жирным выделяется только изменённая часть предложения.
- **Доступ к Bot API режется провайдером.** В РФ диапазоны Telegram (`149.154.160.0/20`, `91.108.4.0/22`) часто недоступны: TCP-коннект к `api.telegram.org` висит и падает с `OSError 121 «Превышен таймаут семафора»` (Windows) или `ClientConnectorError`, при этом обычный интернет работает. Проверка в одну строку: `curl -m 10 -o NUL -w "%{http_code}" https://api.telegram.org/` — `000` значит режут. Обход — `BOT_PROXY` в `.env` (`socks5://user:pass@host:port` или `http://host:port`, нужен `aiohttp-socks`); пустое значение — напрямую. `BotSession` в `tg/main.py`.
- **Если прокси нет, а `api.telegram.org` закрыт — `BOT_API_BASE`.** Это адрес зеркала Bot API (Cloudflare Worker или любой реверс-прокси), `BotSession` подставляет его через `TelegramAPIServer.from_base`, и бот перестаёт зависеть от прямого доступа к Telegram. Пустое значение — стандартный `api.telegram.org`. Токен в зеркало не зашивается: воркер просто переписывает хост и форвардит путь, поэтому `BOT_API_KEY` остаётся только в `.env`. Выбор `BOT_PROXY` против `BOT_API_BASE` — по факту: `curl -m 10 -o NUL -w "%{http_code}" https://api.telegram.org/` даёт `000` в обоих случаях, но WARP из РФ не спасает (`warp-cli registration new` → `Failed to communicate with the WARP API`, а его выход не меняет страну), поэтому на российском сервере рабочим оказывается именно зеркало.
- **Зеркало на Cloudflare душат по адресам, поэтому IP прибит в `/etc/hosts`.** Провайдер режет не весь Cloudflare, а отдельные anycast-префиксы: к «плохому» адресу TCP-хендшейк проходит за 0.1 с, а ответ приходит через 20–40 с или не приходит вовсе (в логе — `Request timeout error`, `Duration 40451 ms`). Причём тормозит даже корень зеркала (`/`), где Telegram не участвует, а `routerai.ru` в это же время отвечает за 0.4 с. Набор плохих адресов меняется в течение дня (замер: `104.18.32.47` — 0.4 с утром и 25 с через час, `104.17.175.85` — 15 из 15 по 0.36 с), поэтому одного `BOT_API_BASE` мало. `deploy/bot-api-ip.sh` замеряет текущий адрес и 8 известных рабочих адресов Cloudflare, при деградации переписывает строку в `/etc/hosts` (маркер `# dnevnik: адрес зеркала Bot API`) и делает `systemctl try-restart dnevnik-bot`; если быстрых нет — ничего не меняет. Таймер `dnevnik-bot-api-ip.timer` запускает его раз в 5 минут и после загрузки. Без root не работает (правит `/etc/hosts`), поэтому запуск руками — через `sudo`. Проверка, что адрес живой: `curl -4 -m 6 -o /dev/null -w '%{time_total}\n' https://tg.german08lib.workers.dev/` — нормальные ~0.35 с.
- **Один потерянный запрос не должен ломать экран.** Пока адрес зеркала был плохим, обработчик мог умереть на `edit_text`/`answer_photo`, и экран оставался прежним, а кнопка крутила «часики». Поэтому отрисовка идёт через `_tg_request` (`TG_ATTEMPTS = 2`, пауза 1 с): `TelegramNetworkError` повторяется один раз, остальные ошибки летят наверх как раньше. `callback.answer()` теперь вызывается **в начале** обработчика, а не после отрисовки — иначе на медленной сети ответ на нажатие опаздывает и Telegram отдаёт `Bad Request: query is too old`. Всплывающие окна (`show_alert`) на ошибках «задание не найдено» / «нет страниц» заменены обычными сообщениями: нажатие уже подтверждено, второе окно Telegram отклонит.
- **Старт polling ждёт Telegram бесконечно.** aiogram не оборачивает в ретраи первый `bot.me()` внутри `dp.start_polling`, поэтому `start_polling()` в `tg/main.py` повторяет запуск сам, без ограничения числа попыток (пауза 2 с, первый сбой пишется `WARNING`, дальше каждый десятый, остальные — `DEBUG`). Ограничивать попытки нельзя: провайдер режет Telegram «окнами» по несколько минут, и бот сдался бы ровно перед тем, как связь вернётся. Отдельной проверки доступности нет — первый же `bot.me()` и есть она, а неудачный коннект обрывается за `CONNECT_TIMEOUT` (10 с). Обработчики при этом падают громко — `aiogram.event: Cause exception while process update` в логе значит, что апдейт дошёл, а ответ отправить не удалось.
- `BotSession` задаёт `sock_connect=10` через `ClientTimeout` в переопределённом `make_request`: без него неудачный коннект висит до системного таймаута ОС (~21 с), и проверка доступности занимает полминуты. `self.timeout` остаётся числом (30 с) — aiogram складывает его с таймаутом long polling, `ClientTimeout` там не переживёт. Общий таймаут сокращён с 40 с: на душащем зеркале запрос либо успевает за секунды, либо висит до обрыва, и дешевле повторить его, чем ждать сорок секунд.
- **Ответ уходит по тому же соединению, что и getUpdates.** `dp.start_polling(bot, handle_as_tasks=False)` — в `tg/main.py` апдейты обрабатываются по одному, а не параллельно. Причина не в экономии: там, где провайдер дропает новые TCP-соединения к Telegram, уже открытое соединение работает — aiohttp держит его в пуле и переиспользует (замер: 12 запросов подряд по нему прошли за 0,00 с, а новый коннект удаётся примерно каждый четвёртый). При параллельной обработке (по умолчанию) отправка ответа требует ВТОРОГО соединения, пока висит long polling `getUpdates`, и падает с `TelegramNetworkError: Request timeout error`, то есть ученик не видит ответа. Плата — пока идёт долгое решение (ИИ может думать минуту), новые апдейты не забираются; Telegram их придерживает и отдаёт после. Если ставить обработку в фон обратно (`handle_as_tasks=True`), ответы снова начнут теряться на такой сети.
- Таймаут коннекта из `BotSession` приходит в лог как `Request timeout error`: aiohttp не различает `sock_connect` и общий таймаут, а aiogram ловит любой `asyncio.TimeoutError` одним сообщением.
- **Соединение нельзя отпускать: его надо держать живым.** aiohttp по умолчанию рвёт простаивающее соединение через 15 с (`TCPConnector(keepalive_timeout=15)`), а решение задачи идёт дольше — единственное рабочее соединение умирало, и ответ снова уходил по новому коннекту, который провайдер режет. Поэтому `BotSession` ставит `keepalive_timeout=300` и запускает `keep_alive(bot)` (задача создаётся в `main()`): когда в пуле нет запросов и соединение молчит дольше `KEEPALIVE_IDLE` (20 с), бот дёргает `getMe` — он идёт по тому же соединению из пула, коннекта не требует и не даёт серверу его закрыть. Пока идёт long polling, пинг пропускается: соединение занято, а второй коннект только помешал бы. Проверено замером: после 45 с паузы `bot.me()` уложился в 0,00 с, то есть соединение переиспользовано.
- `BotSession` дополнительно форсит IPv4 (`family=AF_INET`): на Windows гонка IPv4/IPv6 через happy eyeballs иногда заканчивается тем же таймаутом, даже когда сеть в порядке.

## Стиль кода

- Функции и переменные — `snake_case`, классы — `CamelCase`.
- Асинхронный код: `async def`, `async with SessionLocal() as session`, aiohttp/SQLAlchemy async.
- Модули импортируются как пакеты от `src` (`from db.crud.main import ...`, `from ai.client import ...`).
- Доступ к БД — только через функции в `db/crud/main.py`, логика — по модулям (net/ai/file_handling/tg).
- Промпты — все в `ai/promts.py`, отдельными константами.
- Комментарии и docstring-и — по-русски.
- Неиспользуемое вычищается (удаляем старые модели/функции/файлы, а не оставляем «на память»).
- Секреты — только в `.env`, в коде не хардкодим.

## Известные ограничения / TODO

- **Нет способа перерешать задачу:** ответ лежит в `homework_tasks.solution`, повторный клик отдаёт его из БД. Нужен `force` в `solve_task` и кнопка «🔄 Перерешать» на экране ответа (пункт отложен).
- **Не подготовлены 133 ДЗ** (в т.ч. ~49 с 1 октября): на них нет кнопки «Решить с ИИ». Лечится прогоном `prepare_homework` по пустым — долго и дорого, отложено. Осторожно: guard не даёт перечитывать ДЗ с задачами, для них нужен `--force` (см. ниже про старые страницы).
- **`.doc` (Word 97-2003) не читается.** Это бинарный OLE-контейнер, а не ZIP, как `.docx`, поэтому `_docx_text` (zipfile + XML) его не разбирает; отдельного парсера в проекте нет. Варианты: требовать `.docx`, конвертировать через LibreOffice (`soffice --headless --convert-to docx`) или тянуть `olefile`+парсер — решаем, когда такие вложения реально пойдут.
- **Ссылки (`homework_links`) не скачиваются:** модель видит только заголовок ссылки.
- **Пересказ старых ДЗ не появится сам:** `prepare_homework` не перечитывает ДЗ с задачами, поэтому ранее сохранённые `not_solvable` («прочитать §11») останутся без пересказа. Нужен прогон `--force` по конкретным ДЗ (он обнулит сохранённые решения) или отдельный дешёвый бэкфилл: у `not_solvable` с непустыми `textbook_paragraphs` поставить `retell` и страницы из `structure.json` без ИИ.
- **Первый пересказ скана идёт долго:** текст страниц не кэшируется, поэтому при перерешивании (которого пока нет) его придётся получать заново. Скорость зависит от `OCR_PROVIDER`: `routerai` при `OCR_CONCURRENCY=4` распознаёт ~3 с на страницу (3 страницы физики ≈ 10 с, параграф на 25 страниц ≈ 40–60 с) и стоит ~0,076 ₽ за страницу; `gigachat` бесплатен, но free-тариф пропускает один запрос одновременно (~10 с на страницу, 25 страниц ≈ 4 минуты, параллельные запросы получают 429). Reasoning у OCR выключен, поэтому цена стабильная: с ним она гуляла от 0,077 до 0,13 ₽ за страницу. После выключения reasoning цена почти не зависит от модели (`nex-agi/nex-n2.5-mini` при том же качестве даёт те же ~0,07 ₽), потому что основную часть счёта даёт сама картинка (≈1636 токенов промпта), а не ответ. Если ожидание станет мешать, OCR можно перенести в `prepare_homework`, чтобы воркер готовил текст заранее; если цена — уменьшить dpi рендера (сейчас 180).
- **Химия без учебника:** у предмета `textbook_path = None` и PDF нет, поэтому retell-задачи по химии честно уходят в `not_solvable`.
- **Сужение страниц** может «не найти все targets» → fallback на весь параграф; качество зависит от модели.
- **Индекс заданий — подсказка, а не истина:** бесплатный GigaChat иногда пропускает номера, особенно на страницах с вложенными подпунктами. Тогда `find_pages_by_targets` не находит всё и разбор идёт по страницам параграфа через ИИ (дороже и менее точно), а в крайнем случае берётся весь параграф. Перескан нужной страницы (`python -m ai.scan <book> --from N --to N --force`) чинит индекс для всех будущих заданий; сканировать всю книгу заново не нужно.
- **Старые `textbook_pages`** посчитаны по прежним правилам (до фикса `printed_to_pdf`) — часть задач открывает не ту страницу. Лечится переподготовкой конкретного ДЗ: `python -m ai.prepare <id> --force` (решение при этом обнулится).
- **В тексте задания остаются печатные номера страниц** («на страницах 238–239»), даже если задания на других страницах. В карточке рядом печатается фактический список страниц задания, поэтому автоподмена текста не делается: в английском одно и то же задание ссылается и на упражнения, и на словарь, и слепая замена сломает вторую ссылку.
- **Обработка ошибок ИИ:** в боте ошибка перехвачена («Не получилось решить задание. Попробуй ещё раз»), но повторного авто-запроса и разбора причин (`LengthFinishReasonError` и т.п.) нет.
- **Git не инициализирован.** `.gitignore`, `requirements.txt`, `.env.example` готовы; при `git init` проверить, что `.env` не попал в индекс.
- **Токены дневника светились в `test.py`** (файл удалён) — после перелогина в дневнике обновить `ACCESS_TOKEN`/`REFRESH_TOKEN` в `.env`.
